# Multi-Track Simultaneous PCB Routing: Algorithms and Implementation

## Overview of Multi-Track Routing in PCB Design

Interactive multi-track routing allows a designer to route multiple nets (e.g. an 8-bit bus) together in parallel, rather than one by one. In tools like Altium Designer, you can select a group of nets and route them collectively – as you move the cursor, all selected traces follow in unison, maintaining a fixed spacing and avoiding obstacles as a group. This yields consistent routing topology for bus signals and saves time compared to routing each trace individually[altium.com](https://www.altium.com/documentation/altium-designer/pcb/routing/interactive-multi?srsltid=AfmBOoo_OwCNvbaDXpuyDYrlb08jB1nQLP1qkE30aPeH_0td7yZQ8Ui3#:~:text=When%20routing%20a%20PCB%20it,route%20multiple%20nets%20simultaneously)[altium.com](https://www.altium.com/documentation/altium-designer/pcb/routing/interactive-multi?srsltid=AfmBOoo_OwCNvbaDXpuyDYrlb08jB1nQLP1qkE30aPeH_0td7yZQ8Ui3#:~:text=After%20launching%20the%20command%2C%20you,modes%2C%20switch%20routing%20layers%2C%20etc). Essentially, the router treats the group of nets as a “bundle” that is guided along a path, keeping the traces parallel and obeying design rules (width, clearance, etc.). Key capabilities include: maintaining constant spacing between tracks, simultaneous obstacle avoidance (or push/shove of existing traces), and ensuring the bundle’s overall route meets high-speed layout constraints (like consistent lengths or topology). Below, we break down the core algorithms and strategies needed to implement such a feature, discuss open-source references, and outline how commercial tools likely tackle the problem.

## Core Algorithmic Components for Multi-Track Routing

**1\. Path Planning for Multiple Traces** – At the heart is a path-finding algorithm that can handle **multiple coordinated paths**. Traditional single-net routing often uses maze search algorithms like Lee’s algorithm (breadth-first search on a grid), A\*, or variants of Dijkstra to find a path that meets clearance rules. For multiple simultaneous nets, a straightforward approach is to treat the entire group as one composite entity during path search. For example, some academic routers merge several parallel nets into a “super-net” and route it as one object[mdpi.com](https://www.mdpi.com/2079-9292/12/24/4942#:~:text=also%20enables%20the%20simultaneous%20routing,points%2C%20which%20facilitates%20subsequent%20path). This is akin to routing a *fat trace* that encompasses all tracks in the bundle. The grid-based global router by Yan et al. (2023) explicitly supports simultaneous routing of nets with adjacent start/end points by merging them into a super-net[mdpi.com](https://www.mdpi.com/2079-9292/12/24/4942#:~:text=also%20enables%20the%20simultaneous%20routing,points%2C%20which%20facilitates%20subsequent%20path), then finds a route using a max-flow algorithm (treating the bundle as a single multi-capacity flow)[mdpi.com](https://www.mdpi.com/2079-9292/12/24/4942#:~:text=In%20%2C%20we%20can%20identify,through%20the%20edges%20of)[mdpi.com](https://www.mdpi.com/2079-9292/12/24/4942#:~:text=Due%20to%20the%20strict%20constraints,more%20efficiently%20solve%20the%20problem). In practice, an interactive router might not run a full maze search for each mouse move (which would be too slow), but it can use similar principles incrementally. A typical approach is **incremental path extension**: at each cursor movement, extend the route a small step in the cursor’s direction for the group, using a local search to avoid immediate obstacles. This was described in FreeRouting’s “Dynamic Route” mode: with each cursor move, a new segment is added and then immediately optimized (pulled tight)[freerouting.org](https://freerouting.org/freerouting/manual/assist-manual-routing#:~:text=). For multi-track, the extension step must account for all N tracks – effectively, we extend a “guide path” and position each parallel trace accordingly. Under the hood, path planning may utilize a grid representation inflated to the bundle’s total width (including spacing) so that any planned step has clearance for the whole group. Algorithms like A\* can be adapted by considering the group as one unit (state includes all track positions) – though this becomes high-dimensional, so heuristics are used to keep it tractable. Many tools restrict the routing pattern to 45°/90° angles and user-guided directions, which reduces search complexity. In summary, an effective path planner for multi-routing might combine a **leader-follower** heuristic (more on this below) with fast collision checking, rather than a brute-force multi-agent pathfind which would be NP-hard for large N.

**2\. Spacing Constraint Maintenance** – A primary requirement is keeping a fixed spacing (clearance) between all the tracks in the group. This spacing is defined by design rules (for example, differential pair gap or bus spacing rule)[altium.com](https://www.altium.com/documentation/altium-designer/pcb/routing/interactive-multi?srsltid=AfmBOoo_OwCNvbaDXpuyDYrlb08jB1nQLP1qkE30aPeH_0td7yZQ8Ui3#:~:text=toward%20your%20target%20destination,modes%2C%20switch%20routing%20layers%2C%20etc)[altium.com](https://www.altium.com/documentation/altium-designer/pcb/routing/interactive-multi?srsltid=AfmBOoo_OwCNvbaDXpuyDYrlb08jB1nQLP1qkE30aPeH_0td7yZQ8Ui3#:~:text=,spacing%C2%A0or%20use%20the%20Shift%2BB%20shortcut). The algorithm must maintain these gaps dynamically as the bundle is routed. A simple strategy is to define the relative offsets of each track from a reference position (say track #1’s path) and *treat violations of spacing as collisions*. In other words, each track in the bundle sees the others as moving obstacles at the required clearance. One implementation trick is to use Minkowski sums (inflating obstacles by the clearance distance) and then treat the group’s shape as if it were one “thick” trace. For example, if you have 8 parallel traces each of width *w* and spacing *s*, the overall bundle can be viewed as a ribbon of width `8*w + 7*s` (assuming they’re in one row). By planning a route for this ribbon, you inherently enforce external spacing. Internally, to maintain spacing, the router can either keep the tracks at fixed offset positions or adjust them on corners so that the spacing in the orthogonal direction remains *s*. Maintaining equal gap during bends is non-trivial – the outer tracks in a turn will naturally spread out more than inner ones. A practical approach is a **gateway/anchor system**: define anchor points for each trace at key positions (e.g., at a corner or obstacle entrance) such that the distance between anchor points equals the desired spacing[docs.kicad.org](https://docs.kicad.org/doxygen/classPNS_1_1DP__GATEWAY.html#details#:~:text=Define%20a%20,e.g)[docs.kicad.org](https://docs.kicad.org/doxygen/classPNS_1_1DP__GATEWAY.html#details#:~:text=a%20pair%20of%20points%20,thus%20creating%20a%20differential%20pair). The routing algorithm then connects these anchor “gateways” with parallel segments, forming the bundle. KiCad’s differential pair router uses this idea – it generates candidate gateway points for the pair and then matches them to form a path that maximizes coupling (i.e. maintains tight spacing) and minimizes extra length or corners[archive.fosdem.org](https://archive.fosdem.org/2015/schedule/event/pcb_routing/attachments/slides/796/export/events/attachments/pcb_routing/slides/796/fosdem_router.pdf#:~:text=Differential%20pair%20routing%20%E2%97%8F%20Gateway,force). In multi-track, a similar concept can be generalized: determine waypoints for the whole bus such that from any waypoint to the next, the tracks can be laid in parallel with correct spacing. Data structures for enforcing spacing might include treating each track segment with an attached “keepout” region for other tracks in the group. When moving one track, you also move the keepout regions that the adjacent tracks must occupy. Efficient **interval trees or sweep-line algorithms** can help ensure no two tracks encroach closer than allowed. In summary, spacing maintenance is handled by designing the router to move the tracks as a rigid formation offset by the specified gap, except when adjustments are needed to avoid collisions.

**3\. Collision Detection and Avoidance** – Collision checking for N simultaneous traces is more complex than for one, because a potential obstacle (via, pad, other trace) might intersect *some* of the parallel paths but not others. The router needs to detect collisions for each track and decide how to react in a unified way. Typically, the algorithm will check each prospective segment of each track in the bundle against existing geometry. If any collision is found, the router can do one of several things: (a) **Walkaround** – attempt to detour the entire bundle around the obstacle; (b) **Push** – if in push-and-shove mode, try to move the obstacle (e.g., shove an interfering trace or via aside) to clear the path; or (c) **Split** – allow one or more tracks in the group to temporarily deviate (stagger) to avoid the obstacle, then rejoin the formation. In interactive modes like Altium’s, you can choose a mode such as *Walkaround*, *Hug and Push*, or *Ignore obstacles*, etc., which affects this behavior[altium.com](https://www.altium.com/documentation/altium-designer/pcb/routing/interactive-multi?srsltid=AfmBOoo_OwCNvbaDXpuyDYrlb08jB1nQLP1qkE30aPeH_0td7yZQ8Ui3#:~:text=,without%20causing%20a%20violation%2C%20an)[altium.com](https://www.altium.com/documentation/altium-designer/pcb/routing/interactive-multi?srsltid=AfmBOoo_OwCNvbaDXpuyDYrlb08jB1nQLP1qkE30aPeH_0td7yZQ8Ui3#:~:text=,only%20on%20the%20current%20layer). In walkaround mode, if any track in the group is blocked and cannot go around within rules, the whole group will stop and a blockage indicator is shown[altium.com](https://www.altium.com/documentation/altium-designer/pcb/routing/interactive-multi?srsltid=AfmBOoo_OwCNvbaDXpuyDYrlb08jB1nQLP1qkE30aPeH_0td7yZQ8Ui3#:~:text=,that%20the%20route%20is%20blocked). In push mode, the algorithm will try to shove obstacles: for example, push an interfering trace on another net out of the way for the bundle to pass[altium.com](https://www.altium.com/documentation/altium-designer/pcb/routing/interactive-multi?srsltid=AfmBOoo_OwCNvbaDXpuyDYrlb08jB1nQLP1qkE30aPeH_0td7yZQ8Ui3#:~:text=obstacle%20without%20causing%20a%20violation%2C,hug%20or%20push%20an%20obstacle). This involves a **constraint solver or propagation** – KiCad’s push & shove router propagates a “force” that moves neighboring tracks until a collision-free space is created[archive.fosdem.org](https://archive.fosdem.org/2015/schedule/event/pcb_routing/#:~:text=Interactive%20%28a,tuning%20and%20differential%20pair%20routing). Internally, KiCad uses an *octagonal clearance* model (treating objects with octagonal inflation for clearance) and iteratively moves items along allowable directions[archive.fosdem.org](https://archive.fosdem.org/2015/schedule/event/pcb_routing/#:~:text=Interactive%20%28a,tuning%20and%20differential%20pair%20routing). Such push-shove algorithms are real-time variants of rip-up and reroute: they find a nearby alternative location for the obstacle that still meets all spacing rules (essentially a local re-route of the obstacle trace). Collision detection needs to be extremely fast for interactive use – typically done via spatial indexing (like an R-tree of segments/pads for quick region queries) and using geometry libraries to check overlaps. Some routers discretize the board into a grid (especially autorouters), but modern interactive routers often work with vector shapes directly for precision. A common technique is to pre-calculate “clearance contours” around obstacles. In differential pair or bus routing, an obstacle that falls between the two traces forces them to either split around it or push it. Zuken’s eCADSTAR “Bus Route” feature notes that obstacles not part of the routed set are *automatically avoided*, and individual routes in the bus may be **split to avoid obstacles if necessary**[portal.ecadstar.com](https://portal.ecadstar.com/contents/services/ecs_doc/2025.0/OnlineHelp/en/Content/PCB/command_help/com_semiauto_busroute.html?TocPath=eCADSTAR%20PCB%20Editor%7CProcess%20Flow%20for%20PCB%20Design%20%7CRouting%20and%20Planes%7CManual%20and%20Interactive%20Routing%7C_____17#:~:text=to%20sketch%20an%20approximate%20path,are%20split%20to%20avoid%20obstacles)[portal.ecadstar.com](https://portal.ecadstar.com/contents/services/ecs_doc/2025.0/OnlineHelp/en/Content/PCB/command_help/com_semiauto_busroute.html?TocPath=eCADSTAR%20PCB%20Editor%7CProcess%20Flow%20for%20PCB%20Design%20%7CRouting%20and%20Planes%7CManual%20and%20Interactive%20Routing%7C_____17#:~:text=resolved%20as%20routes%2C%20if%20possible%2C,are%20split%20to%20avoid%20obstacles). This means the algorithm can temporarily break the uniform spacing – e.g., one or two lines go around a via on one side, the rest on the other side – if that avoids a jam (though such topology divergence might be limited to small detours[mdpi.com](https://www.mdpi.com/2079-9292/12/24/4942#:~:text=,are%20illustrated%20in%20Figure%204)[mdpi.com](https://www.mdpi.com/2079-9292/12/24/4942#:~:text=Figure%204,Topology%20forbidden%20when%20avoiding%20obstacle)). In summary, collision handling for multi-track routing requires treating a group of parallel traces as a unit for most cases, but being prepared to locally adjust or push things when one trace’s path is impeded. All of this must respect design rules: no individual trace can violate clearance to *any* obstacle, and no two bundled traces can violate their mutual clearance.

**4\. Push-and-Shove Mechanics** – Push-and-shove deserves special attention as it’s key for interactive routing efficiency. In multi-track mode, push/shove implies moving entire *groups* of existing traces when the bundle needs to pass through. A robust implementation will recursively push obstacles: if trace A in our group hits an obstacle B (another net), and B can be moved (not fixed), the router calculates a new position for B’s segments (often by attempting small shifts or complete reroutes around the bundle). If moving B causes B to collide with C, then C is pushed, and so on – a chain reaction similar to sliding puzzles. This **“force propagation”** approach is how KiCad’s router works[archive.fosdem.org](https://archive.fosdem.org/2015/schedule/event/pcb_routing/#:~:text=board,tuning%20and%20differential%20pair%20routing). The algorithm essentially searches for a cavity or gap to shove things into, ensuring no design rules are broken in the final layout. Data structures like **conflict graphs** can be used: nodes are movable objects (tracks/vias), and edges indicate clearance conflicts; pushing is like re-coloring the graph to resolve the conflict. Real-time performance is critical, so these adjustments are often done with greedy heuristics rather than exhaustive search. For example, shift the interfering segment by one grid step away from the bundle and check clearance; if still colliding, try another direction or propagate the move further down that trace. It’s noteworthy that push/shove with multiple parallel lines can be complex – you might end up pushing an entire *row* of traces aside to make a channel for the new bus. High-end tools manage this well, effectively opening a “tunnel” for the bus. From an algorithmic standpoint, push/shove is not a single algorithm (like A\*), but a suite of local modifications plus continuous DRC checks. After each push or segment addition, a **glossing** (smoothing) algorithm runs to optimize the geometry (removing unnecessary bends, straightening segments)[altium.com](https://www.altium.com/documentation/altium-designer/pcb/routing/interactive-multi?srsltid=AfmBOoo_OwCNvbaDXpuyDYrlb08jB1nQLP1qkE30aPeH_0td7yZQ8Ui3#:~:text=degrees%20only.%20,connected%20to%20or%20in%20the)[altium.com](https://www.altium.com/documentation/altium-designer/pcb/routing/interactive-multi?srsltid=AfmBOoo_OwCNvbaDXpuyDYrlb08jB1nQLP1qkE30aPeH_0td7yZQ8Ui3#:~:text=area%20of%20the%20tracks%20that,directly%20from%20the%20panel%20through). This keeps the routed bus clean and performance high, since it minimizes path length and removes zig-zags that could slow further routing steps. In pseudo-code, a push/hug step might be: “while collision, attempt small displacement of obstacle; if obstacle can’t move (fixed or board edge reached), try bending our trace around (hug); if no solution, report blockage.” Many patents and literature describe push/shove, but specifics are often proprietary. However, Altium’s documentation and KiCad’s open implementation confirm the general approach: treat the routing process as *interactive* and *iterative*, always maintaining DRC (design rule check) compliance or highlighting where it’s not possible[altium.com](https://www.altium.com/documentation/altium-designer/pcb/routing/interactive-multi?srsltid=AfmBOoo_OwCNvbaDXpuyDYrlb08jB1nQLP1qkE30aPeH_0td7yZQ8Ui3#:~:text=,without%20causing%20a%20violation%2C%20an)[altium.com](https://www.altium.com/documentation/altium-designer/pcb/routing/interactive-multi?srsltid=AfmBOoo_OwCNvbaDXpuyDYrlb08jB1nQLP1qkE30aPeH_0td7yZQ8Ui3#:~:text=,only%20on%20the%20current%20layer).

**5\. High-Speed and Synchronization Considerations (Extension)** – While the core question focuses on basic multi-track behavior, it’s worth noting additional algorithmic components if high-speed constraints come into play. Length matching across the bus, for example, might require inserting meanders on shorter traces to equalize lengths. This can be done after the main route is laid down: algorithms can identify the longest trace and then add serpentine tuning patterns to shorter ones to match length (KiCad and Altium provide interactive length-tuning tools). There’s also the matter of **topology matching** – ensuring all bus lines have the same general route shape, number of corners, and layer transitions. This is often desirable for timing and coupling consistency. Some academic solutions explicitly enforce topology matching (same segment count, same layers, preserved order)[mdpi.com](https://www.mdpi.com/2079-9292/12/24/4942#:~:text=,are%20illustrated%20in%20Figure%204). In an interactive router, this is naturally achieved by routing them together, but if one trace detours separately, the topology might diverge (which could affect skew or crosstalk). Advanced algorithms might flag such deviations and either re-route the others similarly or prompt the user. Another component is user interaction design: for example, allowing the user to dynamically adjust spacing during routing (Altium lets you hit *B* or *Shift+B* to widen/narrow the bus spacing on the fly[altium.com](https://www.altium.com/documentation/altium-designer/pcb/routing/interactive-multi?srsltid=AfmBOoo_OwCNvbaDXpuyDYrlb08jB1nQLP1qkE30aPeH_0td7yZQ8Ui3#:~:text=routing,modes%2C%20switch%20routing%20layers%2C%20etc)[altium.com](https://www.altium.com/documentation/altium-designer/pcb/routing/interactive-multi?srsltid=AfmBOoo_OwCNvbaDXpuyDYrlb08jB1nQLP1qkE30aPeH_0td7yZQ8Ui3#:~:text=toward%20your%20target%20destination,modes%2C%20switch%20routing%20layers%2C%20etc)). Implementing that means recalculating the offsets of each trace in real time with minimal delay – essentially just a geometry update, but must be integrated smoothly with collision checks.

## Algorithmic Approaches to Multi-Track Routing

There are several conceptual approaches to implementing multi-track routing, each with pros and cons. It’s possible that commercial tools use a hybrid of these:

-   **“Fat Trace” (Unified Shape) Routing:** In this approach, the entire bundle is treated as one thick shape during pathfinding. You would route a single notional trace whose width equals the total width of the group (including spacings). This simplifies the pathfinding to a single path problem: e.g., run A\* or a maze router once for the big shape. After finding a path for the “fat” trace, it is then split into individual tracks placed within that corridor. The advantage is that the bundle remains perfectly together and obstacle avoidance is unified – if the fat trace fits, all thin ones fit inside it. This approach is essentially what the “super-net” idea in research literature does[mdpi.com](https://www.mdpi.com/2079-9292/12/24/4942#:~:text=also%20enables%20the%20simultaneous%20routing,points%2C%20which%20facilitates%20subsequent%20path), and what the eCADSTAR bus router’s guide path represents (the sketched path width is the minimum needed to include all tracks and spacings)[portal.ecadstar.com](https://portal.ecadstar.com/contents/services/ecs_doc/2025.0/OnlineHelp/en/Content/PCB/command_help/com_semiauto_busroute.html?TocPath=eCADSTAR%20PCB%20Editor%7CProcess%20Flow%20for%20PCB%20Design%20%7CRouting%20and%20Planes%7CManual%20and%20Interactive%20Routing%7C_____17#:~:text=The%20width%20of%20the%20routing,in%20the%20Bus%20Route%20dialog). The downside is that it can be overly conservative: a wide shape might detour around an obstacle that only actually blocks one of the smaller tracks. In tight boards, this can cause the bundle to take longer routes than necessary. Also, splitting the fat trace into individual lines at the detailed routing stage can be tricky around corners or when the path width changes. Commercial tools likely use a fat-trace concept **for the interactive guiding** – i.e., the user effectively drags a wide corridor. Altium’s interactive router shows a “shadow” of the bus while routing, which can be thought of as that corridor. Once you commit segments, the tool lays down each track inside, maintaining clearances.
    
-   **Coupled Multi-Path Routing (Simultaneous A*):*\* This approach attempts to route each net with its own path algorithm but with added constraints that keep them together. One could imagine running N instances of a pathfinder (one per net) in parallel, but adding penalties for diverging from the group or for breaking spacing. The algorithms would coordinate to ensure no two chosen paths violate spacing. This is similar to multi-agent pathfinding in robotics, where each agent (trace) needs a route, and you want them to move in formation. A brute-force joint A\* treating all N traces’ positions as one combined state is theoretically possible, but the state space blows up exponentially with N. Instead, a practical method is sequential A\* with memory of the previous trace’s path: route the first net normally, then route the second net with a bias to stay alongside the first (for instance, limit the search to a “stripe” region next to the first route, and enforce spacing as a hard constraint)[mdpi.com](https://www.mdpi.com/2079-9292/12/24/4942#:~:text=,wires%2C%20obstacles%20and%20other%20elements). Then route the third net next to those, etc. This is a *sequential but coupled* strategy. However, if the second net encounters an obstacle, it might force the first net to adjust as well – meaning you may need backtracking to earlier routed nets to maintain the bundle. Another method is the “negotiated congestion” approach (like PathFinder algorithm used in FPGA routing), where all nets are initially routed (possibly some short-cuts violating spacing), then iteratively adjusted to resolve conflicts. In a bus context, one could initially route each net ignoring the others, then iteratively push them towards equal spacing and parallelism, negotiating any obstacle detours collectively. Some academic work uses a **network flow or ILP formulation** to route buses optimally under constraints (e.g., treating available routing space as capacity for multiple parallel wires)[mdpi.com](https://www.mdpi.com/2079-9292/12/24/4942#:~:text=,Problem%20Modeling)[mdpi.com](https://www.mdpi.com/2079-9292/12/24/4942#:~:text=Due%20to%20the%20strict%20constraints,more%20efficiently%20solve%20the%20problem). These can yield an optimal set of paths for the group but are too slow for interactive use (solving ILPs can take minutes/hours for complex boards[mdpi.com](https://www.mdpi.com/2079-9292/12/24/4942#:~:text=Due%20to%20the%20strict%20constraints,more%20efficiently%20solve%20the%20problem)). In practice, a heuristic coupled routing is more likely: basically, the router tries to route all tracks in lockstep – expanding a wavefront for each trace and disallowing any that break spacing or diverge too far. If one trace’s wave hits an obstacle, the others might pause or slow until a detour is found that all can accommodate.
    
-   **Leader-Follower (Primary Trace with Clones):** A commonly used approach in interactive routing is to designate one trace (often an outermost or center line of the bundle) as the “leader” that the user directly steers. The other tracks are then dynamically placed relative to the leader’s path. For example, if the user is effectively dragging the first net of the bus, the algorithm will mirror its moves for the other nets with the fixed offsets. This works well when the path is relatively clear – it’s straightforward to compute that “trace2 should be 0.2″ below trace1 at all times”, etc. KiCad developers discussing multi-track dragging have described such a scheme: when multiple tracks are selected and dragged, the closest track to the cursor is effectively the leader, and all others move in the same direction, maintaining the initial spacing[mail-archive.com](https://www.mail-archive.com/devlist@kicad.org/msg00321.html#:~:text=My%20solution%20works%20like%20this,same%20distance%20between%20the%20traces)[mail-archive.com](https://www.mail-archive.com/devlist@kicad.org/msg00321.html#:~:text=more%20tracks%20selected%2C%20wait%20for,same%20distance%20between%20the%20traces). When a turn is made (say a 45° bend), all tracks need to pivot together, ideally maintaining spacing throughout the corner[mail-archive.com](https://www.mail-archive.com/devlist@kicad.org/msg00321.html#:~:text=more%20tracks%20selected%2C%20wait%20for,same%20distance%20between%20the%20traces). Implementing this means calculating corner paths that are staggered – the inner track of a turn will cut the corner tighter than the outer track. A simple heuristic is to introduce slight length offsets so that after the turn, the lines realign with equal spacing (often the outer tracks get a tiny bit longer through the corner). Leader-follower is essentially what *manual* routing of a bus is – one usually routes one trace and then copies that pattern for others. The interactive router just automates the copying in real time. The challenge comes when the leader’s straightforward path isn’t feasible for a follower due to an obstacle. In that case, a pure leader-follower might break down (some follower might be forced to fall behind or take a different route). One solution is to momentarily allow that net to diverge (as mentioned under collision handling) and either pause the leader or find a new path that regroups the bundle. In practice, commercial tools likely combine leader-follower with background pathfinding: the user’s motion sets a general direction for the group, but the tool might be running quick path searches for the individual lines a few steps ahead to check feasibility. Altium’s router, for instance, can *converge or diverge* the bus spacing on command (to squeeze through a tight spot or spread out)[altium.com](https://www.altium.com/documentation/altium-designer/pcb/routing/interactive-multi?srsltid=AfmBOoo_OwCNvbaDXpuyDYrlb08jB1nQLP1qkE30aPeH_0td7yZQ8Ui3#:~:text=toward%20your%20target%20destination,modes%2C%20switch%20routing%20layers%2C%20etc), which implies it is recalculating positions of followers on the fly rather than keeping them rigidly fixed behind the leader at all times.
    

**Which approach do commercial tools use?** It appears they use a blend of the above. The eCADSTAR “Bus Route” tool is described as a *semi-automatic sketch router*: the user sketches an approximate path (essentially like dragging a fat trace over the board), then the router “resolves” that into actual routes for each net, avoiding obstacles and splitting routes as needed[portal.ecadstar.com](https://portal.ecadstar.com/contents/services/ecs_doc/2025.0/OnlineHelp/en/Content/PCB/command_help/com_semiauto_busroute.html?TocPath=eCADSTAR%20PCB%20Editor%7CProcess%20Flow%20for%20PCB%20Design%20%7CRouting%20and%20Planes%7CManual%20and%20Interactive%20Routing%7C_____17#:~:text=to%20sketch%20an%20approximate%20path,are%20split%20to%20avoid%20obstacles)[portal.ecadstar.com](https://portal.ecadstar.com/contents/services/ecs_doc/2025.0/OnlineHelp/en/Content/PCB/command_help/com_semiauto_busroute.html?TocPath=eCADSTAR%20PCB%20Editor%7CProcess%20Flow%20for%20PCB%20Design%20%7CRouting%20and%20Planes%7CManual%20and%20Interactive%20Routing%7C_____17#:~:text=When%20you%20complete%20the%20sketched,then%20they%20are%20left%20unrouted). This sounds like a **fat-trace followed by individual A**\*: one wide guide path is chosen, then each net is routed within it, possibly with some adjustments per net if obstacles intrude. Altium’s interactive multi-routing feels more leader-follower while dragging, but under the hood it likely does something similar – treat the whole group as one object for collision checking, and when needed, drop one track’s segment or shove an obstacle. Differential pair routing (which is just a 2-net bus) often uses a leader-follower with symmetry: you route one trace and the other is its mirror, or you route a center line and offset both. Altium and others allow differential pairs to be routed by clicking one net; the pair is routed together. The algorithms there ensure the two traces stay edge-coupled and cornering is handled by bending one trace a bit longer around corners to maintain spacing. For larger buses, a “center-line plus offsets” strategy can be extended: compute a notional center of the bus, route that, and place traces around it. However, if the bus has an even number of lines or must maintain a specific order relative to connector pins, a center-line approach might not directly apply. Instead, one of the outermost lines or a specific net could be the leader. Some autorouters and interactive tools also attempt **auto-reordering** of the bus lines if it helps routing – eCADSTAR can automatically swap the order of signals in the pattern to minimize crossings at the ends[portal.ecadstar.com](https://portal.ecadstar.com/contents/services/ecs_doc/2025.0/OnlineHelp/en/Content/PCB/command_help/com_semiauto_busroute.html?TocPath=eCADSTAR%20PCB%20Editor%7CProcess%20Flow%20for%20PCB%20Design%20%7CRouting%20and%20Planes%7CManual%20and%20Interactive%20Routing%7C_____17#:~:text=Auto%20minimize%20crossed%20connection). This doesn’t change the algorithmic routing of the bundle, but it can simplify the end connections if the bus pins are not in perfect order (this is more of a schematic/assignment problem, though).

In summary, commercial tools likely implement multi-track routing by first defining a **guide path** for the bundle (via user input or an internal algorithm) – effectively treating it like one “object” – and then distributing the individual traces along that path with fixed spacing, using push/shove and detours as needed to keep them all DRC-clean. When one trace of the group cannot continue (e.g., a via is smack in the middle of where that trace needs to go), the router might **pause the entire group’s progress** until the user adjusts the path or it might try an automatic resolution (split that one trace around the via, if possible, as long as topology rules allow it[mdpi.com](https://www.mdpi.com/2079-9292/12/24/4942#:~:text=illustrated%20in%20Figure%204)[portal.ecadstar.com](https://portal.ecadstar.com/contents/services/ecs_doc/2025.0/OnlineHelp/en/Content/PCB/command_help/com_semiauto_busroute.html?TocPath=eCADSTAR%20PCB%20Editor%7CProcess%20Flow%20for%20PCB%20Design%20%7CRouting%20and%20Planes%7CManual%20and%20Interactive%20Routing%7C_____17#:~:text=resolved%20as%20routes%2C%20if%20possible%2C,are%20split%20to%20avoid%20obstacles)). If an automatic fix isn’t possible, typically the group stops – Altium’s router will simply show a blockage marker and not let you plow through a violation[altium.com](https://www.altium.com/documentation/altium-designer/pcb/routing/interactive-multi?srsltid=AfmBOoo_OwCNvbaDXpuyDYrlb08jB1nQLP1qkE30aPeH_0td7yZQ8Ui3#:~:text=,the%20Interactive%20Router%20hug%20existing)[altium.com](https://www.altium.com/documentation/altium-designer/pcb/routing/interactive-multi?srsltid=AfmBOoo_OwCNvbaDXpuyDYrlb08jB1nQLP1qkE30aPeH_0td7yZQ8Ui3#:~:text=obstacles%20to%20continue%20the%20route,routing%20engine%20will%20stop%20at). At that point the user can try a different route, or in push mode, maybe drag a bit more to give the algorithm a hint to push harder or take a slightly different angle. In some cases, one or more nets might get “left behind” if they absolutely cannot follow – eCADSTAR’s documentation mentions that any segments that cannot be completed without errors are left unrouted (and there’s an option to automatically remove such incomplete routes)[portal.ecadstar.com](https://portal.ecadstar.com/contents/services/ecs_doc/2025.0/OnlineHelp/en/Content/PCB/command_help/com_semiauto_busroute.html?TocPath=eCADSTAR%20PCB%20Editor%7CProcess%20Flow%20for%20PCB%20Design%20%7CRouting%20and%20Planes%7CManual%20and%20Interactive%20Routing%7C_____17#:~:text=When%20you%20complete%20the%20sketched,then%20they%20are%20left%20unrouted)[portal.ecadstar.com](https://portal.ecadstar.com/contents/services/ecs_doc/2025.0/OnlineHelp/en/Content/PCB/command_help/com_semiauto_busroute.html?TocPath=eCADSTAR%20PCB%20Editor%7CProcess%20Flow%20for%20PCB%20Design%20%7CRouting%20and%20Planes%7CManual%20and%20Interactive%20Routing%7C_____17#:~:text=Value%20Description%20ON%20When%20the,connected%20to%20the%20end%20point). So the tool might route as much of the bus as it can and drop any traces that got stuck, leaving the designer to finish those manually.

## Key Technical Challenges and Solutions

**Obstacle Handling & Partial Failures:** A critical challenge is what to do when the group encounters a situation where not all traces can proceed. For example, net #3 might be blocked by a via, while nets #1,2,4-8 could go around it fine. There are a few strategies here. One is **all-or-nothing group movement** – i.e., the group acts like a train: if one carriage can’t pass, the whole train stops. This is what happens if you use *Walkaround* mode and don’t allow splitting; it ensures the bundle remains strictly together, but it relies on the user to navigate around the trouble spot. Another strategy is **temporary fanning out**: allow some traces to take a slightly longer path around the obstacle and then rejoin. This is permissible as long as design constraints like topology are not too strict. Figure 4(c) in one paper illustrates that a topology where one trace goes around an obstacle separately *can* be allowed as long as the overall segment count and order are preserved[mdpi.com](https://www.mdpi.com/2079-9292/12/24/4942#:~:text=illustrated%20in%20Figure%204) (the group remains in the same order and same general route, just one had a wider loop). But something like figure 4(d) – where the detour causes a major out-of-sync topology – is forbidden[mdpi.com](https://www.mdpi.com/2079-9292/12/24/4942#:~:text=should%20be%20routed%20in%20the,are%20illustrated%20in%20Figure%204). Implementing this means the algorithm needs to detect when one trace is lagging or detouring, and possibly slow down the others or insert extra bends so they all reach the next alignment point together. This is quite complex to do seamlessly in real-time. In practice, interactive routers often choose to *halt* when a single trace is blocked in a way it cannot resolve by minor pushes. The user then either wiggles the cursor in a different direction (which is essentially manual intervention to find a path that works for all), or the user might exit multi-route mode for that net. Altium, for instance, would highlight the stuck trace in red if it can’t complete; you might then route that one separately or use a different layer. Some advanced tools might automatically drop a via to take the problematic net to another layer, if allowed (this would be an auto-interactive feature akin to partial autorouting). Handling partial failures also involves UI/UX decisions: should the router remove the partially routed segments of the stuck net (as eCADSTAR’s “Remove incompletes” option can do[portal.ecadstar.com](https://portal.ecadstar.com/contents/services/ecs_doc/2025.0/OnlineHelp/en/Content/PCB/command_help/com_semiauto_busroute.html?TocPath=eCADSTAR%20PCB%20Editor%7CProcess%20Flow%20for%20PCB%20Design%20%7CRouting%20and%20Planes%7CManual%20and%20Interactive%20Routing%7C_____17#:~:text=Value%20Description%20ON%20When%20the,connected%20to%20the%20end%20point))? Or leave them as a guide for the designer to manually adjust? There’s also a question of **what if the user continues routing after some nets dropped** – should the remaining ones continue as a smaller group? Typically yes, the tool would continue with the ones that are still following, and possibly reintroduce the dropped one later if it finds a chance.

**Real-Time Performance:** Multi-track routing is CPU-intensive because every move potentially affects N traces and possibly numerous obstacles. To keep the user experience smooth (interactive feedback in real-time), the implementation must be highly optimized. Some techniques to ensure performance include:

-   *Incremental updates:* The router should not recompute everything from scratch on every mouse movement. Instead, it carries a running solution that it updates locally. For instance, if the user moves the cursor 5 mils to the left, the algorithm can extend the existing segments or adjust the last segment rather than recalculating the entire path from the start. This is how interactive single-net routers work – they add segment by segment[freerouting.org](https://freerouting.org/freerouting/manual/assist-manual-routing#:~:text=). For multi-nets, the same applies: you update the last segment (or a couple of segments near the end) for each trace. If push/shove is active, you also incrementally adjust any moved obstacles from their last known positions.
    
-   *Spatial data structures:* using efficient indexing (like R-trees or grid bucketing) for collision detection means you can query “what’s near my new segment” quickly instead of checking every object on the board. KiCad’s router uses a cached geometry model of the board for this purpose, enabling millisecond-range queries for clearance violations.
    
-   *Parallel processing:* Although EDA tools are traditionally single-threaded for such tasks, one could parallelize certain checks (e.g., collision checks for each track in the bundle could be done in parallel threads, since checking net1 vs obstacles is independent of net2 vs obstacles, aside from the minor overhead of threads). In practice, the overhead of thread management might outweigh benefits for small N, but for a large bus one could see some gain on multi-core CPUs. Autorouters sometimes multi-thread different nets; an interactive approach might multi-thread at the sub-net level.
    
-   *Simplified geometry during routing:* When the router is in motion (cursor moving), some tools lower the “glossing” effort to prioritize speed. Altium’s router has glossing levels – at strong gloss it will heavily optimize track shape (which is slower), at weak gloss it does minimal optimization[altium.com](https://www.altium.com/documentation/altium-designer/pcb/routing/interactive-multi?srsltid=AfmBOoo_OwCNvbaDXpuyDYrlb08jB1nQLP1qkE30aPeH_0td7yZQ8Ui3#:~:text=,of%20the%20board%20routed%20quickly)[altium.com](https://www.altium.com/documentation/altium-designer/pcb/routing/interactive-multi?srsltid=AfmBOoo_OwCNvbaDXpuyDYrlb08jB1nQLP1qkE30aPeH_0td7yZQ8Ui3#:~:text=,when%20dealing%20with%20critical%20traces). In real-time, you might keep glossing weak, then when the user finishes the route (mouse up), do a final strong gloss to clean up the tracks. This ensures the frame rate stays high while moving.
    
-   *Limiting search space:* If implementing any kind of search (even a local one to avoid an obstacle), it’s important to set search boundaries. For example, you might limit how far off the direct cursor path the router will go automatically. If the user is dragging mostly a straight line, the algorithm shouldn’t suddenly explore a huge detour 2 inches away; it should wait for the user to guide it. This principle keeps the computations bounded and predictable. It also avoids “surprising” the user with a wild route – the interactive paradigm is WYSIWYG.
    
-   *Data reuse:* If push/shove moves a segment of an existing trace, that trace’s connections might get perturbed. Good implementations keep track of original vs current positions so they can quickly undo or adjust if needed. Essentially, a small backtracking system is at play – something goes wrong, revert a few steps. This is much faster than a global undo since it’s localized.
    

**Maintaining Equal Length / Skew:** If required to keep all the lines equal-length (for high-speed timing), the tool faces the challenge of routing them such that they all arrive together. In interactive use, typically you route the bus first, then use tuning algorithms to add length (meanders) to the shorter ones. Trying to enforce equal length during the initial routing is very hard because it’s a multi-objective problem (you care about path topology and length simultaneously). However, some tools do assist by showing a length gauge and maybe allowing “accordion” adjustments on the fly. Algorithmically, one could treat it as a secondary phase: once the rough route is placed, calculate length differences and then insert serpentine patterns in the straight sections for those that need extra length. KiCad, for instance, offers a differential pair skew tuning tool that can adjust one trace of the pair to match the other[gitlab.com](https://gitlab.com/kicad/code/kicad/-/issues/2005#:~:text=Implement%20PNS%20dragging%20functionality%20for,the%20space%20between%20tracks). For an 8-line bus, you might sequentially tune 7 of them to match the longest. Ensuring equal length is somewhat beyond the scope of the initial routing algorithm and more about post-processing – but it’s a consideration for the overall feature.

**User Interaction Design:** Another challenge is presenting control to the user. Multi-track routing needs ways to let the user adjust spacing, drop a specific net from the group, or change layers with all nets. Typically, hitting the layer-change hotkey will drop vias for all nets to a new layer (if possible) – the algorithm must find viable via locations for each net, ideally in a pattern that maintains spacing (perhaps a dogbone via fanout pattern). If one net can’t drop a via due to a component or obstacle, that might block the whole group’s layer change until resolved. Providing feedback is crucial: highlight which net is blocking if possible. Also, cancellation – the user might want to cancel one trace out of the group if it’s causing trouble; implementing that means the tool should allow “peeling off” one net from the active group. This could be as simple as the user clicking that net’s end, which completes it (maybe to a closer via or stub) and then continuing with the rest. From an algorithm view, it means dynamically altering N (reducing the group size) and possibly recalculating the spacing offsets (e.g., if the middle net of an 8-bit bus is dropped, nets 1-3 and 5-8 now form two smaller groups or one group with a gap where #4 was – the tool might collapse the gap or leave it empty). These edge cases add complexity but are important for a polished user experience.

## Open-Source Implementations and References

Implementing a multi-track router from scratch is a complex task, but there are several resources – both open-source codebases and academic literature – that can provide guidance:

-   **KiCad’s Push-and-Shove Router (C++):** KiCad (open-source PCB tool) includes an advanced interactive router (the PNS – “push and shove” – router) developed by CERN. While KiCad (as of version 7) does *not* yet support multi-net simultaneous routing for general nets, it does support **differential pair routing** and multi-track dragging of existing traces. The differential pair code in KiCad is highly relevant, as it’s essentially the 2-net version of our problem. KiCad’s router uses a “gateway matching” algorithm for diff pairs[archive.fosdem.org](https://archive.fosdem.org/2015/schedule/event/pcb_routing/attachments/slides/796/export/events/attachments/pcb_routing/slides/796/fosdem_router.pdf#:~:text=Differential%20pair%20routing%20%E2%97%8F%20Gateway,force): it generates possible gateway points for the pair (around pads, obstacles, cursor position) and then matches them in a way that maximizes coupling (keeps the pair parallel) and minimizes extra corners/length. The current implementation is brute-force in evaluating gateway pairings[archive.fosdem.org](https://archive.fosdem.org/2015/schedule/event/pcb_routing/attachments/slides/796/export/events/attachments/pcb_routing/slides/796/fosdem_router.pdf#:~:text=cursor,force). This gives insight into how one might handle multiple nets: by generating waypoints and ensuring each net in the group goes through corresponding waypoints, you keep them synchronized. The KiCad source code (in `pcbnew/router/` directory) contains classes like `PNS::DIFF_PAIR` and `PNS::DP_GATEWAY`[docs.kicad.org](https://docs.kicad.org/doxygen/classPNS_1_1DP__GATEWAY.html#details#:~:text=Define%20a%20,e.g)[docs.kicad.org](https://docs.kicad.org/doxygen/classPNS_1_1DP__GATEWAY.html#details#:~:text=a%20pair%20of%20points%20,thus%20creating%20a%20differential%20pair) that implement these concepts. Studying `pns_diff_pair.cpp` and `pns_router.cpp` in KiCad’s codebase would show how the interactive engine extends single-track routing to a coupled pair – including how it maintains gap (`m_gap`) and handles corners. KiCad’s developers have also discussed multi-track dragging; in a mailing list post, one developer outlined a possible approach where on drag, after selecting multiple tracks, the closest track-end to the cursor becomes the “master” and others follow, with turns executed in unison at 45° angles[mail-archive.com](https://www.mail-archive.com/devlist@kicad.org/msg00321.html#:~:text=My%20solution%20works%20like%20this,same%20distance%20between%20the%20traces). This is not yet in production, but the discussion (KiCad issue #14983) reveals practical considerations (like how to handle selection, cursor anchoring, etc.) and might be useful[mail-archive.com](https://www.mail-archive.com/devlist@kicad.org/msg00321.html#:~:text=My%20solution%20works%20like%20this,same%20distance%20between%20the%20traces)[mail-archive.com](https://www.mail-archive.com/devlist@kicad.org/msg00321.html#:~:text=mouse%20button,same%20distance%20between%20the%20traces).
    
-   **FreeRouting (Java, open-source autorouter):** FreeRouting is an open-source autorouter originally written in Java (now on GitHub【24†source】). It’s primarily an automatic router, but it does have an interactive mode for single traces. FreeRouting’s core algorithm is a maze router with iterative rip-up and retry (the “Negotiated A\*” style). While FreeRouting does not explicitly support interactive multi-bus routing, its autorouting logic inherently routes multiple nets and could be studied for how it handles bus-like situations. In particular, FreeRouting’s cost functions and clearance handling might inform how to integrate spacing rules for multiple nets. The FreeRouting documentation notes that it supports differential pair clearance rules (it will treat paired nets with a different clearance), but actual diff-pair routing might not be fully automatic there. Nevertheless, looking at how FreeRouting structures its routing grid, wavefront expansion, and especially how it optimizes (“pull tight” operations to straighten traces[freerouting.org](https://freerouting.org/freerouting/manual/assist-manual-routing#:~:text=)) could be valuable. The project is quite large, but key areas are the `router` package, which contains classes for maze search, cost calculations, etc.
    
-   **Other Open EDA Tools:** gEDA and PCB (older open-source PCB tools) don’t have sophisticated interactive routers comparable to Altium. However, there is **LibrePCB’s router** and some experimental projects that might be exploring this. As of now, KiCad is leading in open-source interactive routing research (with contributions from CERN). Another tool, **Toporouter** (by Intel for FPGA, open-sourced) was a topological autorouter that inspired parts of KiCad’s push-and-shove. It doesn’t explicitly do multi-track, but its approach to obstacles could be insightful (it uses topological transformations of traces to avoid obstacles). The **FOSDEM 2015 talk by Tomasz Włostowski**[archive.fosdem.org](https://archive.fosdem.org/2015/schedule/event/pcb_routing/#:~:text=Interactive%20%28a,tuning%20and%20differential%20pair%20routing) is a great resource – slides are available and they detail data structures for geometry and the push/shove algorithm, which are directly applicable to multi-track routing as well (just extended for groups). The talk also covers length tuning and diff pairs.
    
-   **Academic Research Code:** Academic papers on PCB routing often provide or describe algorithms that could be prototyped. For example, the 2018 ICCAD Contest on PCB Routing had a special problem on bus routing. One solution (Wang et al. 2019) proposed a **DAG-based topology-matching bus router** (ensuring each bus had consistent topology) and a “bus clustering” method to combine buses for efficiency[baloneymath.github.io](https://baloneymath.github.io/files/DAC19_bus.pdf#:~:text=In%20practice%2C%20the%20proposed%20bus,6)[baloneymath.github.io](https://baloneymath.github.io/files/DAC19_bus.pdf#:~:text=5%20CONCLUSIONS%20In%20this%20paper%2C,that%20our%20algorithm%20significantly%20outperforms). While these are global routing algorithms (not interactive), their techniques (like treating a bus as a single unit in certain graph representations, or using rip-up and reroute to fix spacing violations[baloneymath.github.io](https://baloneymath.github.io/files/DAC19_bus.pdf#:~:text=penalty%20cost%20,route%20scheme)[baloneymath.github.io](https://baloneymath.github.io/files/DAC19_bus.pdf#:~:text=5%20CONCLUSIONS%20In%20this%20paper%2C,that%20our%20algorithm%20significantly%20outperforms)) are relevant. Some academic prototypes might be available on authors’ GitHub or as supplementary material. The paper by Yan and Chen (2011) on obstacle-aware bus routing for length-matching (cited in an Iowa State thesis[dr.lib.iastate.edu](https://dr.lib.iastate.edu/bitstreams/baa06fe6-541d-4f4a-888d-94f3083cd518/download#:~:text=,aware%20shortest%20path)) likely had a prototype code; if found, it could offer insight into algorithmically splitting/merging traces around obstacles.
    
-   **Patents and Commercial Documentation:** Sometimes, patents filed by EDA companies reveal their methods. A search in patent databases for “multi-net interactive routing” or “multi-trace PCB routing” might yield descriptions of algorithms (for example, a Cadence or Mentor patent about simultaneous route planning or about push/shove of bus). While not open-source, they can validate the approach you take.
